# การเขียนโค้ดและทดสอบอย่างเป็นระบบ

ใช้ข้อกำหนดนี้เมื่อสร้างหรือแก้ไขโค้ด รวมถึงโค้ดตัวอย่างในคำตอบและไฟล์ทดสอบ เลือกใช้ skill ภาษาไทยหรืออังกฤษเพียงเวอร์ชันเดียว ทั้งสองมีข้อกำหนดเดียวกัน

## หัวไฟล์และคอมเมนต์

- ใส่ข้อความต่อไปนี้เป็นคอมเมนต์หัวไฟล์เพียงหนึ่งครั้งในทุกไฟล์โค้ดที่สร้างหรือแก้ไข:

  `สรวิชญ์ วันเสน รหัสนักศึกษา 673380064-8 sec.1`

- ใช้รูปแบบคอมเมนต์ที่ถูกต้องของภาษานั้น เช่น:

  Python / shell:

  ```python
  # สรวิชญ์ วันเสน รหัสนักศึกษา 673380064-8 sec.1
  ```

  JavaScript / TypeScript / Java / C / C++ / C#:

  ```javascript
  // สรวิชญ์ วันเสน รหัสนักศึกษา 673380064-8 sec.1
  ```

  HTML:

  ```html
  <!-- สรวิชญ์ วันเสน รหัสนักศึกษา 673380064-8 sec.1 -->
  ```

  CSS:

  ```css
  /* สรวิชญ์ วันเสน รหัสนักศึกษา 673380064-8 sec.1 */
  ```

- วางหัวคอมเมนต์เป็นบรรทัดแรกที่ไม่ขัดข้อกำหนดของภาษา หากมี shebang, encoding declaration หรือ directive ที่ต้องอยู่ต้นไฟล์ ให้คงลำดับที่ถูกต้องแล้ววางหัวคอมเมนต์ถัดจากส่วนที่จำเป็น
- เก็บข้อความ ชื่อ รหัสนักศึกษา และ `sec.1` ตามต้นฉบับทุกตัวอักษร ไม่แปลชื่อและไม่เพิ่มหัวเดิมซ้ำ
- ห้ามเพิ่มคอมเมนต์อธิบายโค้ด คอมเมนต์ท้ายบรรทัด คอมเมนต์แบ่งส่วน TODO หรือ docstring ที่ใช้แทนคำอธิบายโค้ด นอกจากหัวคอมเมนต์ที่กำหนด ให้ใช้ชื่อที่สื่อความหมายและโครงสร้างที่อ่านง่ายแทน
- การอธิบายวิธีใช้และเหตุผลทำได้ในข้อความตอบหรือเอกสารแยกนอกโค้ด
- เมื่อแก้ไฟล์เดิม อย่าลบคอมเมนต์เดิมหรือข้อความลิขสิทธิ์โดยไม่เกี่ยวกับงาน คงคอมเมนต์ที่เครื่องมือจำเป็นต้องใช้เพื่อรักษาการทำงาน และเพิ่มเฉพาะหัวที่กำหนด
- อย่าแก้ไฟล์ generated, vendor หรือ third-party เพื่อใส่หัว หากต้องเปลี่ยนโค้ดที่สร้างอัตโนมัติ ให้เปลี่ยนแหล่งต้นทางตามระบบของโครงการ
- ถ้ารูปแบบไม่รองรับคอมเมนต์ เช่น JSON ห้ามแทรกข้อความจนไฟล์เสียหรือเพิ่มข้อมูลปลอมเพื่อแทนคอมเมนต์ แจ้งข้อยกเว้นนั้นในรายงานส่งงาน

## ขั้นตอนทำงาน

1. อ่านโจทย์ ข้อกำหนดโครงการ โค้ดที่เกี่ยวข้อง และวิธีทดสอบที่มีอยู่ก่อนแก้ไข สรุปผลลัพธ์ที่ต้องการ ขอบเขต และเกณฑ์ผ่านให้ชัดเจน
2. วางแผนสั้น ๆ แบ่งงานตามผลลัพธ์ที่ตรวจสอบได้ ระบุไฟล์หรือส่วนที่ต้องเปลี่ยนและวิธียืนยันผล ไม่ขยายงานไปยังส่วนที่ไม่เกี่ยวข้อง
3. สำหรับบั๊ก ให้ทำซ้ำปัญหาหรือสร้าง regression test ที่ล้มเหลวก่อนแก้เมื่อทำได้ สำหรับฟีเจอร์ ให้กำหนดพฤติกรรมที่คาดหวังและกรณีทดสอบก่อนลงมือ
4. เขียนโค้ดเป็นขั้นตอน ใช้รูปแบบและเครื่องมือของโครงการ ลดการเปลี่ยนแปลงที่ไม่จำเป็น และตรวจหัวไฟล์กับข้อห้ามคอมเมนต์ทุกไฟล์ที่แตะ
5. ทดสอบจริงด้วยเครื่องมือที่รันได้ ตรวจผลลัพธ์และ exit code แก้สาเหตุของความล้มเหลว แล้วรันส่วนที่เกี่ยวข้องซ้ำจนผ่านหรือพบข้อจำกัดที่แก้ต่อไม่ได้
6. ตรวจ diff ก่อนส่งงานเพื่อหาการแก้ไขนอกขอบเขต ความผิดพลาด และข้อมูลลับ จากนั้นรายงานผลที่ยืนยันได้

## มาตรฐานการทดสอบ

- ใช้ test framework และคำสั่งที่โครงการมีอยู่ ไม่เปลี่ยนระบบทดสอบโดยไม่จำเป็น
- เลือกการทดสอบตามพฤติกรรมที่เปลี่ยนและความเสี่ยง: กรณีปกติ ค่าขอบเขต อินพุตไม่ถูกต้อง และการจัดการข้อผิดพลาดที่เกี่ยวข้อง รวม regression test ของบั๊กที่แก้
- ทดสอบ integration เมื่อเปลี่ยนสัญญาการเชื่อมต่อหลายส่วน และทดสอบ end-to-end หรือทดลอง flow จริงเมื่อเปลี่ยนเส้นทางใช้งานสำคัญ ไม่บังคับใช้ทุกระดับกับทุกงาน
- รัน formatter check, lint, type check และ build ที่โครงการมีและเกี่ยวข้อง รวมชุดทดสอบเดิมที่เสี่ยงได้รับผลกระทบ
- ตรวจพฤติกรรมและผลลัพธ์ที่ผู้ใช้ต้องการ ไม่เขียน test ที่เพียงคัดลอก implementation หรือทดสอบข้อความหัวคอมเมนต์แทนความถูกต้องของโปรแกรม
- mock เฉพาะขอบเขตที่จำเป็น เช่นบริการภายนอก และระบุชัดว่าผลนั้นไม่ใช่การยืนยันบริการจริง ห้ามใช้ข้อมูลหรือผลรันที่แต่งขึ้นแทนการทดสอบ
- ห้ามปิด ข้าม ลบ test หรือทำ assertion ให้อ่อนลงเพียงเพื่อให้ผ่าน แยกปัญหาเดิมของโครงการออกจากปัญหาที่เกิดจากการเปลี่ยนแปลงครั้งนี้
- หากทดสอบไม่ได้เพราะขาด dependency, credential หรือ runtime ให้บอกสิ่งที่ขาดและการตรวจสอบที่ยังทำไม่ได้ ห้ามอ้างว่าผ่านหรือเสร็จสมบูรณ์ทั้งที่ยังไม่ยืนยัน

## รายงานส่งงาน

ตอบให้กระชับ ระบุสิ่งที่เปลี่ยน คำสั่งที่รันจริงและผลผ่าน/ไม่ผ่าน ข้อยกเว้นเรื่องหัวไฟล์ และข้อจำกัดหรือสิ่งที่ยังไม่ได้ทดสอบ ถ้าไม่มีข้อจำกัดให้ระบุเฉพาะข้อมูลที่มีประโยชน์ ไม่ต้องแสดง checklist ยาว ๆ และไม่อ้าง coverage หรือจำนวน test หากไม่ได้วัดจริง
